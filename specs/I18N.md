# Internationalization

Capy Budget ships a localized UI. English (`en`) is the source language and
fallback; Russian (`ru`) is the second language. Adding a language is a
translation-only contribution — see
`packages/i18n/CONTRIBUTING_TRANSLATIONS.md`.

## Package

`@capybudget/i18n` owns all translation infrastructure and is consumed by both
`packages/app` and `apps/demo` — one source of truth, no duplicated catalogs.
It exports the i18next config (self-initializing on import), the `I18nProvider`,
the `useTranslation` / `useLocale` / `useAiLanguage` hooks, `setLocale`, and the
supported-locale metadata.

## Catalogs

JSON, namespaced by area: `packages/i18n/locales/<lang>/<namespace>.json`.
Namespaces: `common` (nav + shared action buttons), `settings`, `budget`,
`analytics`, `import`, `capy`, `onboarding`, `help`. Keys are grouped by feature
within a namespace, not flattened.

The Help screen is a hybrid: its short chrome (header, section anchors, demo
link) lives in the `help` namespace, but the long-form "How budgeting works"
prose lives in per-locale content modules
(`packages/app/src/components/help/help-guide-content.<lang>.ts`, selected off
the active locale) — paragraphs of copy don't belong in catalog JSON.

`react-i18next.d.ts` derives `t()` key types from the `en` catalogs, so keys are
checked under strict mode and autocomplete — a wrong key fails typecheck. Other
locales are validated for key parity at runtime, not by types.

`resources.ts` imports the `en` catalogs statically (they're the typed source of
truth) and discovers every other locale's catalogs with `import.meta.glob`,
keyed off `SUPPORTED_LOCALES`. So adding a language is a JSON-plus-one-registry-
line change — there is no hand-maintained per-locale import block to forget, and
a contributor can't ship a locale that silently falls back to English.

## Namespace convention

A component declares its **primary area namespace first, then `common`**, and
reaches shared keys with the `common:` prefix:

```ts
const { t } = useTranslation(["budget", "common"])
t("transactions.title")   // budget — the primary namespace, unprefixed
t("common:actions.save")  // shared button, explicitly prefixed
```

A component that only needs one namespace passes it directly —
`useTranslation("settings")` or, for the nav (which is pure `common`),
`useTranslation("common")`. Never rely on the bare `useTranslation()` /
`defaultNS` form: name the namespace so the lookup is explicit and greppable.

## Locale preference

Language is a device/user preference (not per-budget): persisted in
`localStorage` under `capybudget.language`. On first run it defaults to the
detected webview/OS locale (`navigator.language`), normalized to the supported
set with `en` fallback. The Settings ▸ General **Language** picker writes the
preference and applies it live via `i18next.changeLanguage`; `useLocale`
re-renders consumers on the switch. (Currency, by contrast, stays per-budget in
`budget.json`.)

## Formatting

Money and dates are locale-aware without coupling `@capybudget/core` to app
state: the locale is threaded in as a parameter. `formatMoney` /
`formatMoneyCompact` and `formatDateLabel` / `formatMonthLabel` take an optional
locale (default `en-US`); the app passes the active language via the currency
context (`useFormatMoney`) and the calendar component. Under `ru`, amounts render
with space grouping and a comma decimal (e.g. `1 250,00 ₽`); the currency symbol
and its position are unchanged. Plurals use i18next's `Intl.PluralRules`
(`one`/`few`/`many`/`other`).

### `useFormatters()`

`hooks/use-formatters.ts` is the single render-edge entry point for
locale+currency-bound formatting. It returns a pre-bound bundle — `{ money,
moneyCompact, percent, date, month, monthShort }` — composing the existing
`useFormatMoney` (currency context), `useFormatPercent`, `useLocale`, and the
core date helpers as internals. The public surface is small and the internals
are swappable; components read `money(cents)` / `date(isoYmd)` instead of
re-threading locale and currency at each call site.

The seam matters: `money` / `moneyCompact` read the currency context, so the
hook is only valid under a `CurrencyProvider` (the budget surface). `percent` /
`date` / `month` / `monthShort` depend on locale alone. A surface outside the
currency context that needs only those may keep calling `useFormatPercent` /
`useLocale` directly. Range / week / drilldown-subtitle labels take a per-call
translator and stay in the analytics adapters (`format-range.ts`,
`use-analytics-labels.ts`), not in this hook.

## Canonical-display translation

Some user-facing strings originate in `@capybudget/core`, not the catalogs:
category and group names are free strings the user can rename, account-type
labels key off a fixed enum, and analytics bakes English fallbacks
("Unknown"/"Uncategorized") and month labels into its series. Core stays
locale-agnostic and keeps emitting canonical English — series-matching joins
(the compare chart, import/AI matching) depend on those stable strings — so the
localization happens at the render edge, by canonical match.

The app owns a central display layer:

- `lib/display-names.ts` holds the canonical name set (the seeded category names
  and the group names, including the `Archived` sentinel) and exposes
  `useCategoryDisplayName()` / `useGroupDisplayName()` / `useAccountTypeLabel()`.
  A display hook returns `(stored) => isCanonical(stored) ? t(key) : stored`: a
  stored name that exactly equals a canonical default renders its translation,
  and a renamed or user-created name renders verbatim, never translated. The
  catalog keys live in the `budget` namespace (`canonicalCategory.*`,
  `canonicalGroup.*`, `accountType.*`), with the canonical English string as
  both the key and the `en` value. The enum→key lookups are typed key-maps
  (see below), so the compiler — not a runtime test — pins each tuple to its
  enum and each value to a real key.
- `components/budget/analytics/use-analytics-labels.ts` localizes the
  analytics-emitted strings the same way: `useCategorySeriesLabel()` maps the
  empty-id Uncategorized bucket and canonical categories to `analytics:*`,
  `useMonthLabel()` / `useWeekLabel()` re-derive a locale-aware chart-axis label
  from the point's ISO `date` (the English `month` field core carries is never
  shown), and `useBasisLabel()` / `useBasisOptionLabel()` localize the budget
  basis options. The "Unknown" merchant bucket localizes off `getTopMerchants`'s
  `isUnknown` flag rather than a display-string compare.

The principle is uniform: **core data stays canonical English; only the
rendered string is translated, and only when it matches a canonical default.**
The stored CSV value is unchanged everywhere else.

## Typed key-maps

Mapping an enum to a catalog key is done with a **typed key-map**, never a
dynamic `t(\`foo.${id}\`)`. A map literal typed `satisfies Record<Enum,
NsKey>` — where `NsKey` is `lib/i18n-keys.ts`'s `BudgetKey` / `AnalyticsKey` /
`SettingsKey` / `CapyKey` (each `ParseKeys<ns>`, i18next's union of that
namespace's valid keys) — makes the compiler enforce two things at once:
exhaustiveness (every enum member is mapped) and key validity (every value
resolves to a real key). Keys are unprefixed, matching `t()` called with that
namespace as primary. The account-type / canonical-category / canonical-group
lookups (`display-names.ts`), the basis labels (`use-analytics-labels.ts`), the
settings-section labels (`settings-screen.tsx`), and the tool labels
(`tool-labels.ts`) all follow this pattern. Because the types now guarantee
what runtime lockstep tests used to assert, those tests are gone; the remaining
display tests cover behavior (canonical-match vs verbatim passthrough,
translation correctness).

## Semantic-label adapters

Beyond the canonical-display hooks, structural and formatted copy is reached
through **semantic-label adapters** — `labels.allAccounts()`,
`labels.transactionCount(n)`, `analyticsLabels.month(date)` — so a component
names the concept, not the catalog key. `lib/use-budget-labels.ts` covers the
budget shell's route chrome (the All-Accounts header, its transaction count,
the account not-found state), shared by both the `packages/app` and `apps/demo`
route mirrors.

The boundary is deliberate. An adapter earns its place only for (a) domain
concepts with data/matching semantics, (b) formatted values, and (c)
structural or recurring chrome that's easy to miss in a sweep — route headers,
empty / not-found states, axis labels. **Ordinary one-off leaf copy stays raw
`t()`.** Wrapping every string in an adapter is an anti-goal: it buries the
catalog key behind indirection without buying type-safety or reuse. Adapters
extend the existing modules (`display-names.ts`, `use-analytics-labels.ts`) or
live in a focused `use-*-labels` module per area; they are not one mega-object.

## AI language

Capy replies in the active language. The English name of the language
(`useAiLanguage`) threads into the chat and import system prompts
(`buildSystemPrompt`, `buildImportSystemPrompt`), which add a single
respond-in-language instruction for any non-English language. Tool descriptions
and enum values stay English — the models are cross-lingual. The active language
joins the chat session signature, so switching rebuilds the session.

## Guardrail

`npm run i18n:check` validates key parity across every non-`en` locale against
`en`, per namespace, failing on any missing or extra key. It also cross-checks
the `locales/` directories against `SUPPORTED_LOCALES`, so a registered locale
with no catalog (or a catalog for an unregistered locale) fails too. On top of
base-key parity it checks plural *completeness*: every plural group must cover
exactly the categories that locale's `Intl.PluralRules` declares (`one`/`other`
for `en`, `one`/`few`/`many`/`other` for `ru`) — base-key parity strips the
suffix and can't see a missing required form, so this is a separate pass. The
parity logic lives in `scripts/parity.ts`; `check-parity.ts` is the CLI wrapper
and `parity.test.ts` runs the same assertion under vitest. So drift fails the
normal `npm test` gate and CI's dedicated `i18n:check` step — not just a
separately remembered command.
